# Проверка доставки последовательного источника — 21.11.2026

Причина: `Serial.read(256)` с `timeout=0.2` ждёт 256 байт либо таймаут даже после LF.
Короткие строки поэтому поступали пачками. Интервал пачек превышал `max_gap_s=0.12`,
мешал окну устойчивости и отменял обучение/распознавание.

## Исправление

`read(max(1, min(256, in_waiting)))` ждёт один байт на пустом порту и читает только
уже доступные байты. Таймаут 200 мс ограничивает ожидание пустого порта и остановки,
но не задерживает законченную строку. Поток не опрашивает пустой порт активным циклом.
Сборка LF/CRLF и пачек сохранена, незавершённый хвост не теряется между чтениями.
Сохранена прежняя защита: хвост более 4096 байт выдаётся как есть и очищается
(не более 4352 байт при чтении до 256). При остановке незавершённый хвост отбрасывается.

Порт закрывается в `finally` рабочего потока, stop ждёт завершения чтения с конечным
таймаутом. Отложенная доставка после stop подавляется. Ошибка чтения/`in_waiting`
передаётся ядру с готовым текстом: прежняя lambda теряла переменную `exc` после except.
Штатная остановка не публикует ошибку порта. Ошибка открытия по-прежнему поднимается
вызывающему коду. Пороги жестов, часы ядра и протокол ESP32 не менялись.

## Воспроизводимость

Из корня, в окружении с requirements-dev.txt:

```powershell
cd host
python -m pytest -q
cd ..
python tools/measure_serial_loopback.py --samples 100 --source-ref 2e8e21a
python tools/measure_serial_loopback.py --samples 100
```

Измеритель берёт старый `_reader` непосредственно из git ref, не меняя checkout.
Время — от записи строки в программный loopback до вызова on_raw в asyncio;
оно включает планировщик ОС. Нет требования доставлять с точностью таймера Windows.
CI также выполняет отдельный loopback-замер на 30 строках на каждой ОС.

Детерминированный транспорт реализует ожидание read(size) до накопления size байт
или таймаута по управляемым часам. На `_reader` из исходного main регрессия коротких
строк и оба сценария обучения падают (3 failed): первая строка с временем 100.02
доставляется в 100.20. В интеграционных сценариях последняя строка обучающего окна
приходит в 102.00 вместо 101.84: тест останавливается на проверке времени доставки.
После исправления все три проходят, обучение завершается saved.
Это проверка старого кода, а не только искусственного интервала.

Переносимые тесты дополнительно проверяют разрезанную строку, пачку LF/CRLF,
незавершённый хвост, ограничение буфера, пустой порт, stop/restart, ошибки чтения
и запроса доступных байт, отложенное уведомление после except и его путь в ядро.
Через реальные SerialSource → parser → Engine на временной SQLite с фиксированными
open=[200,300], fist=[1200,1300] проверены обучение и профиль glove, короткое/достаточное
удержание, одно событие и отсутствие повторов. Разрывы 160 мс без такта во время паузы
и 600 мс с тактом сбрасывают автомат; восстановление в позе не запускает аудио,
новый выход и удержание снова разрешают одно событие. Аудио заменено заглушкой.
Пользовательская база не используется.

## Ограничения и отдельный вопрос BLE

Физический USB COM, Bluetooth SPP и BLE, реальные сенсоры и аудиоустройство не проверены.
Loopback доказывает исправление программного накопления, но не ограничивает задержки
драйвера, радио, ESP32 или занятого цикла asyncio. Время устройства не синтезируется.

Отдельно: docs/protocol.md уже фиксирует пакетную доставку BLE с интервалами до 143 мс
по записи 25.10. Это может превышать max_gap_s=120 мс и мешать обучаемым жестам.
Текущий BLE notify сразу передаёт данные в on_raw; ожидания read(256) в нём нет.
Совместимость BLE при таких пачках требует самостоятельного исследования на записи/
физическом устройстве и не считается исправленной этим изменением. Код BLE не изменён.
