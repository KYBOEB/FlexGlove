# Промпты для запуска этапных чатов

Перед стартом: откройте новый чат в проекте Claude «FlexGlove», подключите к нему папку репозитория `flexglove`
(актуальный `main`). Документы проекта Claude (roadmap, decisions, protocol, этот файл) новее копий в репозитории —
первым коммитом этапа их нужно перенести в `docs/`.

---

## Этап 2 — связь с реальным прототипом (2 сенсора)

```
Этап 2: связь приложения FlexGlove с реальным прототипом перчатки (сейчас 2 гибких сенсора). Ветка stage-2-prototype.

Контекст от планировщика:
- v0.2.0 принимает любое число каналов 1–8. Планировщик проверил сквозной сценарий на эмуляции 2 каналов через
  последовательный порт в трёх форматах (строка "v1;v2", метки "S1:…"/"S2:…", строки с отладкой "#"): 2 канала,
  сгиб 0→100 %, комбинации 10/01/11, жест 11 → ARM, полусжатие → команда захвату ≈ 50 %, запись CSV, потеря связи
  → заморозка и снятие ARM — всё работает. Живого BLE-подключения к перчатке ещё не было.
- Найден баг: элементы с атрибутом hidden, у которых в CSS задан display (например, .demo-strip), не скрываются —
  плашка «Демо-режим» видна при подключённой перчатке.
- Найдена проблема логики: с 2 сенсорами «оба согнуты» — это одновременно жест 11 и полное сжатие захвата, то есть
  каждое сжатие переключает команду.

1. Прочитай README.md, CLAUDE.md, docs/decisions.md, docs/protocol.md, docs/analysis/2026-10-25-sensor-stream.md.
   Из документов проекта Claude перенеси в docs/ актуальные roadmap.md, decisions.md, protocol.md,
   cowork/STAGE_KICKOFF.md (первый коммит этапа).
2. Задачи:
   a. Исправить баг с [hidden] (глобальное правило [hidden]{display:none!important}) и проверить все такие места.
   b. Разделить сжатие и команды (решение D-21, предложи окончательную схему и согласуй со мной до кода):
      в настройках выбрать «пальцы сжатия» и «пальцы команд»; пока управление активно, команды срабатывают только
      удержанием комбинации ≥ 1 с и не срабатывают от изменения пальцев сжатия; тесты на сценарий «сжал кулак —
      команда не сработала».
   c. Сессия с прототипом (я рядом с перчаткой): подключение по BLE («Найти устройства»; если не видно — порт),
      по «Отладке потока» определить фактический формат и частоту; если формат не распознаётся — добавить в parser.py с тестом.
   d. Устойчивость: автопереподключение BLE при обрыве (3 попытки), понятные сообщения; предупреждение в интерфейсе,
      если канал «молчит» (прошивка шлёт только при изменении) или частота < 20 Гц.
   e. Запись со сгибами (5 с покой → 5 × (сгиб 2 с / разгиб 2 с) → 5 с покой) по каждому сенсору; скрипт разбора
      tools/analyze_recording.py (уровни покоя/сгиба, размах, шум, время нарастания, дрейф, графики PNG);
      выводы и при необходимости новые пороги processing.py — в docs/analysis/2026-11-XX-prototype-2ch.md.
   f. Протокол v0.3 (гибкие + MPU6050, черновик в docs/protocol.md): парсер принимает строку
      "v1;v2|ax;ay;az;gx;gy;gz"; IMU пока только разбирается, хранится в состоянии и показывается в «Отладке потока»
      и в записи CSV (доп. колонки); тесты. Формат подтвердить с Захаром.
3. Чек-лист проверки с прототипом (результаты — в analysis-файл этапа):
   - перчатка видна в поиске BLE; Python-программа Захара и телефон от перчатки отключены (ESP32 держит одно подключение);
   - «Отладка потока»: формат text-values, 2 канала, 45–55 сообщений/с, «не распознано» = 0;
   - «Каналы и пальцы»: S1 и S2 назначены реальным пальцам;
   - при подключении ладонь раскрыта (автокалибровка), затем калибровка «Ладонь» и «Кулак»;
   - каждый палец: сгиб 0 → 100 % на графике, комбинации 10 / 01 / 11;
   - команда ARM жестом; сжатие ведёт захват; сжатие кулака не переключает команды;
   - выключение перчатки → «Нет связи», захват заморожен, ARM снят; включение → переподключение;
   - запись CSV открывается в Excel.
4. Критерий готовности: живая перчатка с 2 сенсорами управляет захватом и командами; чек-лист пройден; запись
   со сгибами разобрана; все тесты зелёные; демо-режим работает; версия 0.3.0 в CHANGELOG.
Сначала план и вопросы, потом работа. В конце — отчёт по docs/cowork/STAGE_REPORT_TEMPLATE.md.
```

## Этап 3 — база алгоритмов фильтрации и распознавания

```
Этап 3: база алгоритмов фильтрации и распознавания данных из потока. Ветка stage-3-dsp. Железо не нужно —
работаем на записях из data/recordings, host/tests/data и синтетике.

Цель: вместо «зашитой» обработки в processing.py — модуль host/flexglove/dsp/, в котором фильтры и распознаватели
являются взаимозаменяемыми блоками; любую комбинацию можно включить настройкой и оценить на записи.

1. Прочитай README.md, CLAUDE.md, docs/architecture.md, docs/decisions.md (D-13, D-17…D-21), docs/protocol.md (v0.3),
   docs/analysis/*, host/flexglove/processing.py, engine.py, control.py.
2. Задачи:
   a. dsp/filters.py: общий интерфейс (reset, process(x, t) → y) и блоки: медиана, Хампель (выбросы), экспоненциальное
      сглаживание, One-Euro фильтр (мало дрожания в покое, мало задержки в движении), фильтр нижних частот 2-го порядка
      (биквад, без scipy), мёртвая зона. Конвейер Pipeline собирается из JSON-описания, например
      [{"type":"median","n":5},{"type":"one_euro","min_cutoff":1.0,"beta":0.01}].
   b. dsp/calibration.py и dsp/normalize.py — перенести калибровку и сгиб 0..1 из processing.py без изменения поведения
      (все текущие тесты проходят без правок).
   c. dsp/features.py: признаки по окну (среднее, СКО, размах, скорость изменения); dsp/segmentation.py: детектор
      «покой / движение».
   d. dsp/recognizers/: общий интерфейс «отсчёт → события»; перенести текущие распознаватели (порог с гистерезисом,
      комбинация пальцев с удержанием); заготовка интерфейса для будущих (kNN поз, динамические жесты) — без реализации.
   e. dsp/orientation.py (ядро для этапа 4): оценка смещения гироскопа в покое, комплементарный фильтр и Madgwick,
      операции с кватернионами, перевод в углы (крен, тангаж, рысканье). Тесты на синтетических вращениях
      (известный угол → оценка в пределах 2°), проверка дрейфа рысканья при неподвижности.
   f. Офлайн-оценка: tools/evaluate.py запись.csv --pipeline конфиг.json → отчёт (шум в покое, задержка по ступеньке,
      число ложных переключений, графики PNG). Генератор синтетики для тестов (ступенька, рампа, шум, выбросы).
   g. Интеграция: engine использует dsp; пресеты конвейера («Базовый» = текущий, «One-Euro», «Сильное сглаживание»)
      выбираются на вкладке «Сигналы» и сохраняются; график показывает выход выбранного конвейера.
   h. Документация: docs/architecture.md (раздел dsp), docs/dsp.md — как добавить свой фильтр/распознаватель за 10 минут.
3. Критерий готовности: все прежние тесты зелёные без правок поведения; новые тесты на каждый блок; evaluate.py
   выдаёт отчёт на записи Захара и записи этапа 2; пресеты переключаются в интерфейсе; демо-режим работает;
   сравнение «Базовый vs One-Euro» на реальной записи — в docs/analysis.
Сначала план и вопросы, потом работа. В конце — отчёт по шаблону.
```

## Этап 4 — MPU6050 и 3D-модель руки (черновик, уточнится по отчётам этапов 2–3)

```
Этап 4: MPU6050 и 3D-модель руки, повторяющая движения кисти. Ветка stage-4-imu-3d.

1. Прочитай README.md, CLAUDE.md, docs/protocol.md (v0.3), docs/decisions.md (D-17, D-19, D-20), docs/dsp.md,
   host/flexglove/dsp/orientation.py, отчёты этапов 2–3 в docs/analysis.
2. Задачи:
   a. Ориентация в ядре: сырые IMU → калибровка смещения гироскопа (2 с покоя при подключении и кнопкой) →
      Madgwick/комплементарный (из dsp/orientation.py) → кватернион 50 Гц в состоянии; кнопка «Обнулить положение»
      (текущая поза = исходная); честная подсказка, что рысканье у MPU6050 медленно дрейфует.
   b. 3D-рука: Three.js из web/vendor/ (без CDN), рука из примитивов: ладонь + 5 пальцев × 3 фаланги с шарнирами,
      сгиб каждого пальца 0..1 → углы суставов; белый матовый материал, мягкий свет, светло-серый фон, мягкая тень —
      как на референсе (картинка приложена к чату; сохрани её в docs/background/hand_reference.png). Плавность: сферическая интерполяция кватерниона каждый
      кадр, 60 к/с. Если WebGL недоступен — 2D-силуэт.
   c. Пульт: 3D-рука вместо 2D в карточке «Рука оператора» (2D-силуэты остаются в карточках комбинаций);
      поворот кисти (крен) → поворот захвата в рабочей зоне через контроллер (ограничения те же).
   d. Демо: имитация IMU (плавные наклоны/повороты, шум, смещение гироскопа) — 3D-рука двигается без железа.
   e. Запись/воспроизведение CSV с колонками IMU; тесты на разбор, ориентацию и запись.
3. Критерий готовности: с прототипом и в демо рука на экране плавно повторяет наклоны и повороты кисти и сгибы
   пальцев; задержка визуально незаметна; дрейф рысканья измерен и описан; тесты зелёные.
Сначала план и вопросы, потом работа. В конце — отчёт по шаблону.
```

Промпты этапов 5–6 планировщик готовит по итогам отчётов.
